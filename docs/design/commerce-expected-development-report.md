# 电商经营 Agent：预期开发报告

> 状态：2026-09-30 阶段规划。本文安排接下来几轮的目标与验收，不代表待办功能已经实现；以代码、测试和实际演示为准。当前定位为个人学习与求职展示，商业化只是长期方向。

## 结论

先证明**商品销售、热点与选品建议**在历史真实数据上可信，再让 Talk 在受约束的指标语义内更好地理解问题，最后交付外部用户可实际体验的演示。只有取得有授权、持续更新的商家数据后，才启动真正的组织隔离、行动反馈与图记忆试点。卖家履约和差评可以成为后续证据能力，但不取代现阶段的商品经营主链路。

## 当前基线与缺口

| 已有能力 | 尚不能据此宣称 |
| --- | --- |
| Olist 历史订单导入、DuckDB 只读商品事实、品类销售、等长窗口趋势、热点与选品规则；Talk 已有三项轻量指标代号 | 实时行情、利润/库存判断、因果效果或跨平台泛化 |
| Benchmark Talk/Plan 工作台、管理员 Plan 审批、追加式演练情景与离线反思 | Talk 是开放式问答 Agent；演练是商家真实执行或经营反馈 |
| 滚动时间留出回测、14 个固定 Talk 案例、人工审查量表及原始 CSV 销售对账 | 已有独立人工验收；自动通过等于建议有效 |

目前 Talk 主要由关键词选择确定性只读工具。Benchmark Plan 的 practice 记录明确是 `benchmark_simulation`；`merchant` 路径尚无 Store 授权和持续数据。原总体规划中“卖家履约与差评诊断是第一链路”的说法与已确认的商品经营方向不一致，应在第一轮同步校正。现有餐饮功能暂不删除，不将其旧口径包装成电商能力。

## 接下来四轮

### 第一轮：可信度与案例验收

- 冻结一批由人审阅的、按提问截止时间截断的案例；从已有 12 个自动案例扩展，先核对数值口径、来源、缺失能力、拒答和误导性建议，再逐步达到总体规划所提的 50–100 例规模。标注答案、所需数据、允许的结论与失败类型，不把模型自己的输出当标准答案。
- 覆盖商品/SKU、品类、时间边界、取消订单、低样本、成本库存缺失和跨项目请求；必要时用独立原始数据计算做对账，保存不含原始订单与个人信息的汇总结果。
- 修订总体规划的主链路描述，并建立自动检查与人工判定的分开记录。**验收：**能公开说明哪些问题答对、哪些必须拒答、剩余风险是什么；同一份 Olist 留出集不用于反复调阈值后声称泛化。

### 第二轮：有界语义与证据化 Talk

- 已完成第一版轻量指标代号：`commerce.product_sales`、`commerce.product_trends`、`commerce.hot_products`。下一步补定义版本、币种、状态、时间窗、可用维度与来源；自然语言别名继续映射到受限 `QuerySpec`，由现有事实提供器执行，不让模型提交任意 SQL。
- 在解析、执行及结果三个环节校验允许的范围、快照、资源预算和对账关系；回答显式展示指标定义、历史时间窗、证据及不能推断的事项。模型若参与措辞，不得补造事实或越过工具结果。
- **验收：**同义提问落到相同指标口径；超范围或含糊问题澄清/拒答；越权、无来源数值和不受控 SQL 为硬失败。优先扩展现有确定性路径，而不是先搭重型数仓。

### 第三轮：可复现的求职展示

- 将数据获取与许可边界、导入、评测、登录、Talk→Plan→审批→历史演练整理为可重复的演示流程；补实际浏览器走查，覆盖普通用户不能使用 Plan 与后端不可用时的提示。
- 解决公网前端与本地后端的可达性问题：当前浏览器 API 默认地址为 `127.0.0.1:8000`，外部访客不会因此连到开发者本机。优先评估**明确标记为静态/只读的公开样本演示**；若需要在线真实交互，再单独决定受控托管后端、鉴权、流量和成本预算。不把预计算结果伪装成实时 Agent 请求。
- **验收：**新访客按说明可完成演示或明确看到只读边界；无原始 Olist 数据、个人凭据、本地数据库或 DuckDB artifact 进入公开部署与 Git。

### 第四轮：有条件的 ToB 基础验证

- 前提是取得明确授权且能持续更新的商家数据。先定义 Organization/Store/Project/Snapshot 归属、角色与会话范围，建立跨租户读取的负面测试，再考虑真实行动、执行与结果分开记录。
- 只有结构化事实和更正历史不足以完成具体关系检索任务，且人工评测显示收益时，才试点“原始记录→待核验主张→确认事实→失效”的图化记忆；订单与指标仍由权威事实层计算。
- **验收：**有授权、撤销和审计路径，隔离测试无越权，能区分建议、采纳、执行和自然结果变化；否则维持现有轻架构，不提前引入 OIDC、Temporal 或 Graphiti 服务。

## 排序与停止条件

第一轮的失败样本决定第二轮应改善哪些问法和口径，第二轮的受约束结果决定第三轮可以诚实展示什么；第四轮不设无数据也必须启动的时间表。若人工案例不能证明相对确定性报表的增益，应收窄 Agent 表述和范围；若公开演示无法安全提供在线后端，就明确采用只读样本演示。每轮保留现有餐饮回归，不以增加框架数量作为进度指标。
