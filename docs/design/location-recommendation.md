# 双模式选址与行政区自动推荐设计

## 1. 目标

在现有开店前分析中增加统一的选址引擎，支持两种入口：

- 手动选址：用户输入具体地址或坐标，系统深度评估该点位。
- 自动推荐：用户指定城市、行政区和经营条件，系统推荐 3 至 5 个值得继续看铺的候选商圈。

自动推荐只输出候选商圈或片区中心点，不输出具体出租铺位。用户选择候选商圈后，转入手动模式，补充实际租金、面积和成本，完成铺位级财务评估。

## 2. 产品原则

1. 百度 POI 是商圈外部证据，不是真实客流、订单量、营业额、租金或开店成功率。
2. 竞争门店越少不一定越好。零竞品可能代表需求不足，评分关注竞争平衡而非单纯低密度。
3. 机会评分、财务可行性和数据可信度分别展示，不允许高商圈分掩盖亏损风险。
4. 所有结论必须关联查询范围、关键词、观察时间、来源和证据有效期。
5. 原始供应商响应不进入长期存储，只保存标准化指标、必要证据和警告。

## 3. 用户流程

### 3.1 手动选址

用户输入：

- 城市、行政区、详细地址或 BD-09 坐标。
- 经营品类、计划客单价和目标客群。
- 月租金、面积、人工、其他固定成本、预计毛利率和营业天数。

系统流程：

1. 将地址解析为 BD-09 坐标；已有坐标则跳过解析。
2. 在 300、500、800 和 1500 米圈层采集竞品、交通和配套 POI。
3. 运行多关键词分页检索并按 POI `uid` 去重。
4. 构建竞争、需求代理、交通、价格和业态特征。
5. 计算机会评分、数据可信度和财务可行性。
6. 输出建议开、调整后再开或不建议开，并列出现场核验问题。

### 3.2 自动推荐

用户输入：

- 城市和行政区。
- 经营品类、计划客单价和目标客群。
- 分析半径和候选数量，候选数量默认 5，最大 10。
- 可选财务假设：毛利率、人工、水电、其他固定成本和目标日订单。缺少这些数据时不输出租金上限和财务结论。

系统流程：

1. 使用百度区域检索在指定行政区检索商场、地铁站、写字楼、社区、学校等候选锚点，首版最多保留 30 个原始锚点。
2. 按 400 米聚类半径合并过近锚点，并保留可解释的代表中心点。
3. 对初筛候选点运行低成本特征采集，保留排名前 10 的候选点。
4. 对前 10 个候选点执行完整多关键词、分页和圈层分析。
5. 输出排名前 3 至 5 的候选商圈、推荐理由、风险和数据可信度。
6. 用户选择候选商圈并转入手动选址，补充具体铺位与财务数据。

## 4. 数据采集

### 4.1 竞品关键词

系统按品类维护关键词集合。茶饮首版使用：

- 奶茶
- 茶饮
- 现制饮品
- 果茶
- 饮品店
- 咖啡
- 甜品

关键词分为直接竞品和替代竞品。所有结果按 `uid` 去重，保留命中关键词集合，避免同一门店被重复计数。

### 4.2 候选锚点

行政区自动推荐首版使用以下锚点类型：

- 购物中心和商业综合体。
- 地铁站和主要公交枢纽。
- 写字楼和产业园。
- 居住社区。
- 高校和主要学校。
- 医院、景区等高频公共设施。

候选锚点只是生成搜索中心的依据，不直接等同于消费需求。
候选生成依赖百度区域检索接口；现有圆形区域检索继续用于候选点周边的深度分析，两者不能混用。

### 4.3 数据有效期

- POI 竞争与配套数据默认有效期为 7 天。
- 地址解析结果可以长期复用，但需保留坐标系和解析来源。
- 未过期、查询参数完全匹配的快照优先复用。
- 关键词、半径、坐标或评分版本变化时不得复用旧评分结果。

## 5. 特征模型

### 5.1 竞争结构

- 直接竞品数量。
- 替代竞品数量。
- 唯一品牌数量。
- 连锁品牌占比。
- 同品牌重复门店数量。
- 各距离圈层的竞品数量。
- 距离衰减后的竞争强度。
- 价格区间和计划价格重合度。

竞争平衡度使用可配置的品类基准区间。竞品过多表示拥挤，竞品过少表示需求未经验证，两端均扣分。

### 5.2 需求代理信号

- 写字楼、产业园和办公设施密度。
- 居住社区密度。
- 学校和高校分布。
- 商场和购物中心分布。
- 医院、景区和公共设施分布。
- 与目标客群匹配的配套业态密度。

报告统一使用“需求代理信号”措辞，禁止显示为真实客流量。

### 5.3 交通便利性

- 最近地铁站距离。
- 300 米和 500 米内公交站数量。
- 停车场数量和距离。
- 首版使用直线距离；后续可通过步行路线 API 增加步行时间。

### 5.4 价格和评价可信度

- 竞品价格中位数、四分位区间和价格覆盖率。
- 计划客单价与商圈价格区间的重合程度。
- 评分必须结合评论数量和字段覆盖率解释。
- 缺少评论数量的评分不得作为高权重优势或风险依据。
- 营业状态为空时标记为未知，不默认为正常营业。

## 6. 评分与结论

### 6.1 机会评分

首版采用 100 分制：

| 维度 | 权重 |
| --- | ---: |
| 竞争平衡度 | 25 |
| 需求代理信号 | 25 |
| 交通便利性 | 20 |
| 价格带匹配 | 15 |
| 周边业态协同 | 15 |

评分必须返回各维度原始指标、子分和解释，不只返回总分。

### 6.2 数据可信度

数据可信度独立计算，至少考虑：

- 分页覆盖率。
- 关键字段覆盖率。
- 查询关键词覆盖范围。
- POI 观察时间和有效期。
- 营业状态、价格和评论量的缺失比例。

首版可信度采用 100 分制：分页覆盖率 30 分、关键字段覆盖率 25 分、关键词覆盖率 20 分、数据新鲜度 15 分、营业状态与评论量覆盖率 10 分。每个子分必须返回原始覆盖率，不允许只返回总分。

数据可信度低于 60 时不得输出确定性的开店建议，只能输出“继续调研”。

### 6.3 财务可行性

自动推荐阶段没有实际租金，系统根据客单价、毛利率和固定成本假设输出建议租金上限，不填造当地真实租金。

手动铺位评估阶段计算：

- 日保本营业额。
- 日保本订单数。
- 实际租金与建议租金上限的差距。
- 资金安全期和投资压力。

最终建议需要同时满足数据可信度门槛和财务可行性规则。

首版结论门槛：

- 建议开：数据可信度不低于 60、机会评分不低于 70，且手动铺位财务测算可行。
- 调整后再开：数据可信度不低于 60，机会评分为 50 至 69，或财务参数存在可调整缺口。
- 不建议开：数据可信度不低于 60，机会评分低于 50，或财务测算明确不可行。
- 继续调研：数据可信度低于 60，或缺少形成财务结论所需的关键输入。

这些门槛是首版可解释规则，必须通过真实区域对照测试校准，不能宣传为统计意义上的成功概率。

## 7. 系统组件

### 7.1 后端

- `GeocodingClient`：地址与 BD-09 坐标转换。
- `CandidateGenerator`：行政区候选锚点检索、聚类和初筛。
- `PoiCollector`：多关键词分页检索、标准化和 `uid` 去重。
- `LocationFeatureBuilder`：构建竞争、交通、价格和业态特征。
- `LocationScorer`：机会评分、可信度和风险规则。
- `LocationAnalysisService`：组织手动分析和自动推荐流程。
- `LocationEvidenceVerifier`：校验结论是否有对应证据。

现有 `BaiduMapClient`、`ExternalContextAnalyzer`、`ExternalContextSnapshotService` 和参考数据仓库继续复用，不在 API 路由中重复实现供应商逻辑。

### 7.2 API

建议增加：

- `POST /pre-open/location/manual-analysis`
- `POST /pre-open/location/recommendations`
- `GET /pre-open/location/analyses/{analysis_id}`

自动推荐请求返回候选列表及分析 ID。完整结果持久化后可被手动选址请求引用，避免重复采集。

### 7.3 前端

开店前页面增加分段控制：

- 手动选址。
- 自动推荐。

自动推荐结果展示排名、候选区域名称、中心点、机会评分、数据可信度、推荐理由、风险和“评估具体铺位”操作。第一版使用列表和结构化报告，地图可视化不作为首版阻塞项。

## 8. 降级与错误处理

- 百度配置缺失：返回配置错误，不启动实时采集。
- IP、权限或配额错误：返回供应商错误分类，不进行无意义重试。
- 网络超时或服务端错误：有限指数退避重试，随后使用未过期快照。
- 无快照：使用城市和品类参考数据，并标记为低可信度降级结果。
- 行政区候选不足：返回已有候选和缺失原因，不填充虚构候选。
- POI 字段缺失：保留空值并降低可信度，不用默认值制造完整性。

## 9. 性能与配额控制

- 自动推荐先低成本初筛，再对前 10 个候选点深度分析。
- 相同查询参数在有效期内复用快照。
- 限制行政区、关键词、分页和候选数量。
- 对同一项目的重复提交使用幂等键。
- 记录调用次数、延迟、错误类型和快照命中率，但不记录 AK。

## 10. 验收标准

### 10.1 手动选址

- 地址和坐标输入均可完成分析。
- 同一门店被多个关键词命中时只计数一次。
- 报告展示多距离圈层、价格、交通、业态、可信度和财务指标。
- 数据不足时只输出继续调研，不输出建议开店。

### 10.2 自动推荐

- 用户指定城市和行政区后可获得 3 至 5 个候选商圈。
- 候选点位于指定行政区，且过近候选已聚类去重。
- 每个候选包含评分拆解、证据、风险和可信度。
- 候选可以无损转入手动铺位精评。

### 10.3 测试

- 百度调用使用合成响应和 `httpx.MockTransport` 测试。
- 增加分页、关键词去重、锚点聚类和评分边界测试。
- 增加快照复用、过期、供应商失败和降级测试。
- 使用成都高新区至少 3 个真实区域执行受控烟雾测试。
- 实时烟雾测试只在显式配置 AK 时运行，不进入默认测试套件。

## 11. 实施边界

首版不实现：

- 具体商铺出租信息和真实租金抓取。
- 真实客流、订单、营业额和闭店率推断。
- 全城无限范围搜索。
- 自动签约或替代现场调研。
- 面向客户长期转售原始百度 POI 数据。

## 12. 推荐实施顺序

1. 完善手动单点的多关键词、分页、去重和圈层分析。
2. 增加地址解析、选址特征和新评分模型。
3. 实现行政区候选锚点生成、聚类和低成本初筛。
4. 实现候选深度分析、排序和手动精评转换。
5. 接入财务模型、租金上限和最终建议。
6. 完成前端双模式入口、候选列表和报告展示。
7. 使用真实区域对比结果校准阈值和权重。
