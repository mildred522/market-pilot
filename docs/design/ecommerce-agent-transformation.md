# Market Pilot：电商经营 Agent 转型规划

> 状态：2026-09-28 决策提案；本文描述目标架构和验收路径，不代表功能已实现。现有餐饮功能、接口和评测仍以代码及现行文档为准。

## 结论与定位

目标是把 Market Pilot 从单店餐饮经营诊断转向**可追溯、可评测、可持续跟进的电商卖家经营 Agent**。差异化不在于叠加图数据库或自然语言转 SQL，而在于：真实订单上的确定性口径、可核对的证据链、受控查询、跨周期的行动反馈，以及不会把商家一句话升级为组织事实的记忆机制。

三个取舍的决定：

| 方向 | 收益 | 代价与边界 | 决定 |
| --- | --- | --- | --- |
| 餐饮转电商 | 可用真实公开订单验证履约、评价和卖家分析；未来可接授权商家数据 | 现有开店、菜品、外卖口径大量失效；历史数据不证明建议带来经营改善 | 先做一条电商垂直链路，不一次性重写或删除餐饮能力 |
| Hermes 式沉淀 + Graphiti 式时序图 | 保留商家目标、事实更正、行动与结果之间可追溯的关系 | 抽取错误、权限、时间、冲突、成本和运维复杂度上升 | 借鉴机制，先小范围试点；订单和指标仍由 SQL 提供权威结果 |
| 指标“代号层” + SQL 门禁 | 统一业务语义并限制查询的表、粒度、租户和资源消耗 | 指标版本、维度和来源映射需要长期治理；规则过严会拒绝合法问题 | 优先建设轻量语义层和运行时门禁；不为 Olist 样本先引入重型数仓 |

产品第一条链路为**卖家履约与差评诊断**：给定卖家和截止时间，识别延迟、低评分及相关订单，输出计算口径、证据、不确定性和下一步排查建议；后续追踪行动是否执行及结果是否变化。不得把相关性描述为干预的因果效果。

## 现状与迁移边界

- 当前 `Order`、`MenuItem`、`Review` 及开店前模型是餐饮语义；经营页面接受订单、菜品成本和评论三类 CSV，单文件上限 5 MB。Olist 原始文件不能直接上传，也不能将商品、卖家强行映射为菜品、门店后复用毛利和堂食/外卖指标。
- 当前记忆是 SQL 中的对话、确认的项目资料和注册指标历史；文档知识的 Qdrant RAG 与经营记忆是不同用途。图记忆是候选增量，不替代现有审计和知识来源。
- `metric_registry` 当前约束的是报告指标路径与解释，并非任意数仓查询的语义层。现有 Agent 安全评测主要使用合成数据；真实数据评测须另建独立的案例与门禁，不应改写原有基线来伪装进展。
- 在新链路通过验收前保留餐饮功能；用显式 `restaurant` / `ecommerce` 领域边界拆开模型、指标、工作流和界面。旧能力何时退役依据产品选择和迁移结果决定，不靠全局替换词语。

## Olist 真实数据：获取、使用和限制

来源：[Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)。它提供 2016–2018 年约十万笔匿名化巴西电商订单，包含商品、卖家、支付、配送和评价；不是实时数据，也不是餐饮门店数据。数据集页面标注 **CC-BY-NC-SA-4.0**；仅按许可范围开展原型验证，商业产品使用须另行确认授权。原始文件和 Kaggle 凭据均不提交仓库。

在仓库根目录按 [Kaggle CLI 认证说明](https://github.com/Kaggle/kaggle-cli/blob/main/docs/README.md) 配置账号后运行：

```bash
python -m pip install kaggle
mkdir -p data/olist
kaggle datasets download -d olistbr/brazilian-ecommerce -p data/olist --unzip
```

也可在数据集页面手动下载并解压到 `data/olist/`；该目录已在 `.gitignore` 中排除。命令的 `--unzip` 用法见 [Kaggle CLI 数据集说明](https://github.com/Kaggle/kaggle-cli/blob/main/docs/datasets.md)。

| 原始文件 | 连接键 | 用途 |
| --- | --- | --- |
| `olist_orders_dataset.csv` | `order_id` | 状态、购买时间、实际/预计送达时间 |
| `olist_order_items_dataset.csv` | `order_id`、`seller_id`、`product_id` | 卖家商品行、价格、运费 |
| `olist_order_reviews_dataset.csv` | `order_id` | 订单评分与评价文本 |
| `olist_order_payments_dataset.csv` | `order_id` | 付款方式与订单支付额 |
| `olist_products_dataset.csv` | `product_id` | 商品品类 |
| `olist_sellers_dataset.csv` | `seller_id` | 卖家标识与所在地 |

以**卖家 + 订单商品行**为最细分析粒度，再关联订单和商品。订单、商品行、付款和评价存在一对多关系：先按各自粒度聚合，再连接，禁止直接跨表求和造成重复计数。整单支付和整单评价不可无依据地全额分摊、归因到某个卖家；多卖家订单应单独标识，必要时排除卖家级归因。商品价格与运费不等于卖家实收或净利润；数据没有可靠采购成本、库存、平台抽佣及实际干预记录，因此不得计算真实毛利、补货效果或建议带来的因果增益。金额以源数据币种与口径呈现，不擅自换算成人民币。

第一轮验证可选定单卖家订单集，按历史时间切片提问：“截至该周末，哪些订单和商品出现履约或低评分异常，证据是什么？”下一时段数据只能用于事后评测，不能进入当时的检索或记忆。公开数据证明分析是否可复核；真实商家持续授权与建议效果仍需另行试点。

## 目标数据与取数链路

```text
源数据与授权 → 原始留存 → 规范化电商事实表/维表 → 指标代号层
                                                   ↓
用户问题 → 受约束的 QuerySpec → SQL 编译与执行前门禁 → 只读查询
                                                   ↓
结果粒度校验 → EvidencePack/运行轨迹 → Agent 结论 → 行动与反馈记录
```

事实表至少区分订单、订单商品、付款、评价及履约事件；记录来源、商家租户、事件时间、导入时间和版本。先以现有技术栈能承载的关系型存储或分析引擎验证口径；当真实数据量、并发、刷新要求证明需要时，再选数仓和编排工具。

代号层用稳定且带版本的 `metric_id`、实体、维度、过滤器、时区、币种、时间窗、聚合粒度和定义替代随意的中文别名；别名只参与解析，最终执行以注册定义为准。例如“销售额”必须先明确是商品标价小计、付款总额，还是某类订单的卖家商品金额，否则询问用户或拒答。`QuerySpec` 只能引用许可的代号、维度和范围；模型不生成可执行 SQL。

**门禁是服务端运行时机制，不只是 Git hook：**

1. 解析后：按角色和租户检验可用的代号、字段、粒度、时间范围与敏感数据。
2. 执行前：由可信编译器生成参数化 SQL；校验语法树、表/列和连接白名单、租户条件、行数、超时和扫描预算。只读数据库账号、表权限和租户隔离是独立的强制边界，不能只依赖字符串过滤或 AST 检查。
3. 执行后：核验返回的币种、单位、粒度、空值与对账关系，记录指标定义版本、查询指纹、参数、数据快照和证据引用；不满足契约则拒绝输出确定性结论。
4. CI：增加指标契约、越权查询、重复计数、注入、预算和跨租户评测；本地 hook 可加速反馈，但不能替代运行时门禁和 CI。

## ToB 记忆：Hermes 沉淀流程与 Graphiti 时序图

借鉴 [Hermes 的有界记忆、会话检索和后台回顾](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory/)，而不是直接接入它的个人 Agent 运行时。Hermes 的记忆/skill 写入可由开关控制审批；ToB 不能采用个人资料、默认自由写入、自动更新 skill 的组织级默认行为。[Graphiti](https://github.com/getzep/graphiti) 提供 episode、实体关系以及事实的时间有效性，用作关系检索与冲突追溯；LLM 提取的图边并不自动等于经营事实。

| 状态 | 含义与存储 | 升级门槛 |
| --- | --- | --- |
| 原始记录 | SQL/对象存储保留授权来源、发言人、事件与版本；不把整库订单复制到图 | 原样留存、可撤销和审计 |
| 待核验主张 | 从记录抽取的候选；只用于审核，不作为结论证据 | 有来源引用、租户范围和冲突检查 |
| 经确认事实 | 商家有权角色确认，或由注册指标在指定快照验证；图存实体关系、来源、有效时间和失效历史 | 明确确认人/规则、`valid_at`、观察时间和失效策略 |
| 行动与反馈 | 建议、采纳、执行、后续结果分别记载 | 不把结果变化自动归因为建议 |
| Playbook | 具有适用条件、证据与失效条件的可复用流程，独立于图事实 | 跨案例评测、去除商家专有信息、人工审查和版本发布 |

ToB 调整原则：

- 个人界面偏好、门店经营事实、企业规则分层，低优先级内容不得覆盖高优先级规则；店员的一句话不能自动成为全组织事实。事实更正保留旧版本及失效时间。
- 所有查询和晋升按 `tenant_id`、门店/企业范围、操作者角色及数据用途鉴权；Graphiti 的 `group_id` 可辅助分区，不能代替服务端鉴权。默认禁止跨租户召回、共享原始图边或案例。
- 不把聊天文本、评价中的命令当作系统指令；候选记忆不得写回受保护的 SQL 代号、权限规则或工具代码。跨商家流程发布需要审查许可、隐私、代表性与适用范围。
- 当前项目的结构化 SQL 会话、指标历史和更正机制继续提供审计底座；图仅覆盖商家目标、确认事实、建议与反馈等确有关系检索价值的内容。文档 RAG 继续负责外部资料，不作为商家经营事实来源。

## 评测、验收与推出顺序

维持现有餐饮测试及合成 Agent 安全门禁，新增独立的真实电商评测；不能把“指标算对了”等同于“经营建议有效”。第一批建议人工标注 50–100 个按时间截断的案例，记录所需数据、正确口径、证据和应当拒答的边界。

| 阶段 | 交付与进入下一阶段的条件 |
| --- | --- |
| 0. 数据与许可 | Olist 下载说明、字段契约、许可边界和可复现的样本切片；不提交原始数据 |
| 1. 电商垂直链路 | 新订单/商品/评价模型，单卖家履约与差评诊断，确定性计算和证据行；旧餐饮链路仍可运行 |
| 2. 代号层与门禁 | 版本化指标口径、受约束 `QuerySpec`、只读执行、租户鉴权及执行前后测试；越权与无来源数值为硬失败 |
| 3. 记忆试点 | 目标、事实更正、行动、反馈的候选/确认/失效闭环；与纯 SQL 记忆比较准确率、延迟和运维成本 |
| 4. 商家验证 | 有授权的增量经营数据与人工工作流；观察建议采纳、执行与结果，不声称无对照的因果改善 |

贯穿各阶段的可观测指标：数值和证据准确率、拒答正确率、跨租户越权次数、重复计数和口径冲突次数、过期记忆召回率、事实更正成功率、响应延迟及每次分析成本。越权读取、伪造证据、错误归因和未经批准的组织记忆/流程发布为零容忍门禁；其余阈值应在真实基线上制定，不沿用合成用例得分。

**停止条件：**如果受许可的数据无法覆盖拟做的决策、真实案例相对确定性报表没有可测增益、图记忆对事实追溯没有净收益，或门禁无法证明租户隔离，就停在已验证的较轻架构，不为“新潮”继续堆基础设施。旧餐饮能力的退役、数据迁移和品牌改名要作为独立产品决策，不能与原型验证捆绑上线。
